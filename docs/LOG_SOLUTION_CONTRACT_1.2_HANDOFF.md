## 1. 給辨識開發者的重點

- 不用 OCR 判斷 READY／BUSY，以四格黑白狀態標記為依據。
- READY 是「可以接受新一輪」；不是「一定有結果」，也不是「本輪 PASS」。
- BUSY 的正常監控圖樣必須表示「已完成本輪來源準備，可以讓 ATE 開測」，不能只表示收到命令。
- 「待確認」對外屬 BUSY，但禁止開測／取用結果；其畫面有獨立圖樣。
- 「正常可交付」與「人工停止可交付」都是 READY，必須有不同機器圖樣；後者須明確回報上位機。
- TESTING 是通道狀態，不是另一種整輪黑白圖樣，也不是交付結果的必經條件。
- 藍框排數標記、紅框狀態標記、左右定位點各有用途，不能互相替代。

## 2. 使用者截圖中的三種標記

| 標記 | 用途 | 判讀內容 |
| --- | --- | --- |
| 藍框：水平兩格 | 排數標記 | 黑白＝一排；白黑＝兩排。不是 READY／BUSY。 |
| 紅框：2×2 四格 | 整輪狀態標記 | 待命、監控、待確認、正常可交付、人工停止可交付。 |
| 左右黑底內嵌白小格 | 定位點 | 找出位置、方向、比例；不是程式工作狀態。 |

藍／紅框是使用者截圖註記，不是要加入 App 的彩色辨識框。橋接不得依賴這些彩色外框。

排數標記避免把「第二排遭遮擋」誤認成「本來只有一排」。定位點仍須先通過方向與畫質檢查，才能採樣狀態格及結果色帶。

## 3. 五種整輪狀態：已確認語意

下列名稱是文件中的辨識名稱；既有程式 enum、TCP 欄位與 HMI 文案須在實作時對齊，不表示它們現在已存在。

| 辨識名稱 | 儀器狀態／HMI | 意義 | 橋接動作 |
| --- | --- | --- | --- |
| STANDBY | READY／待命 | 可接受新一輪，沒有可交付的本輪結果 | 可以發開始監控命令，不取用色帶殘留結果 |
| MONITORING | BUSY／監控中 | 本輪來源已準備完成，可可靠收集之後的 Log | 確認是本次開始後，通知上位機可觸發 ATE |
| REVIEW | BUSY／待確認 | 衝突或警報尚待人員處理；讀檔可能繼續或已停止 | 通知上位機暫停後續動作，不交付結果 |
| COMPLETE | READY／完成 | 本輪完整結果可交付，且無待確認；不是人工停止 | 穩定性與同輪性驗證後交付全部結果 |
| MANUAL_STOP_COMPLETE | READY／人工停止 | 人工停止；結果已完整定案，且無待確認 | 交付全部結果，明確回報「人工停止」，不可只報一般完成 |

規則：

1. 有待確認衝突／未確認警報時，REVIEW 優先，不能因其他欄位為可交付就顯示 COMPLETE。
2. COMPLETE 不是全 PASS；FAIL／NOTEST／TIMEOUT 也可能是合法完整結果。
3. 人工停止後若仍有待確認，先 REVIEW，處理完才 MANUAL_STOP_COMPLETE。
4. 正常開始／完成及人工停止，通道、色帶、整輪快照、硬碟稽核重建必須一致。
5. 背景保存不單獨阻擋結果交付或下一輪 READY；保存異常仍須可見、可恢復，正常關閉仍依既有完整保存政策。
6. 啟動失敗不得偽造 MONITORING 或完整結果。故障畫面與恢復流程細節仍待實作規格補齊。

## 4. 四格圖樣配置

讀取順序固定為：左上、右上、左下、右下。B＝黑，W＝白；數值 1＝黑，0＝白。

| 狀態 | 上排 | 下排 | 位元順序 | 確認狀態 |
| --- | --- | --- | --- | --- |
| STANDBY | B W | W B | 1001 | 沿用 1.1 |
| MONITORING | B B | W W | 1100 | 沿用 1.1 圖樣，收緊成來源已準備完成 |
| REVIEW | B W | B W | 1010 | 沿用 1.1 |
| COMPLETE | W B | B W | 0110 | 沿用 1.1，保留一般可交付語意 |
| MANUAL_STOP_COMPLETE | W W | B B | 0011 | **新增圖樣建議，尚待使用者確認** |

第五種圖樣示意（建議）：

```text
┌─────┬─────┐
│ 白  │ 白  │
├─────┼─────┤
│ 黑  │ 黑  │
└─────┴─────┘
```

此配置保留既有四個圖樣，五種都維持恰好兩黑兩白；任何單一格的黑白翻轉不會變成另一個合法圖樣。但它不是錯誤校正保證，不能省略畫質、穩定影格及遮擋檢查。

未定義圖樣（包括 0101）、缺格或低對比都回 unknown，不猜成最接近狀態。舊 1.1 consumer 不認得第五種圖樣，必須先更新橋接才能部署 App。

## 5. 排數、幾何與取樣

### 5.1 已沿用的內容

- 每排固定 10 格；容量 1–10 顯示一排，11–20 顯示兩排。超出配置容量的位置為黑色，不是產品 FAIL。
- 排數：BW＝一排、WB＝兩排；BB／WW／缺失／低對比均拒判。
- 狀態格 2×2，每格 10×10 Tk 單位，間隔 2，白色 quiet zone 2，總尺寸 26×26。
- 灰階 0–80 判黑、176–255 判白，81–175 不可靠；這是最低取樣規則，不是實際 JetKVM 壓縮容差已驗收。
- Tk 單位不是實體像素；橋接必須由定位點量測比例。

### 5.2 幾何變更：方向已同意、精確座標待驗

移除 `KVM RESULT` 字樣，左定位點移至第一格色帶正上方；其他定位點、排數格、狀態格及結果色帶位置維持。

| 項目 | 現行 1.1 幾何 | 1.2 狀態 |
| --- | --- | --- |
| 左定位點 | (82, 2)，22×22 | 新 x 未定；左緣須不大於第一格色帶左緣；與右點同高 |
| 右定位點 | (320, 2)，22×22 | 維持 |
| 排數格 | (130, 2)，26×14 | 維持 |
| 狀態格 | (278, 0)，26×26 | 維持 |
| 色帶 | 第一格 x=0、首排 y=34；格寬34、高26，列距27 | 維持 |

四周須至少 2 單位白留白，維持左右不對稱內嵌白格；不與其他標記／色帶重疊。第一格 x=0 與左側留白須以父框範圍、實際畫面及裁切驗證，不可直接假設負座標有效。

新定位點距離尚未定稿；consumer 不得把「約 320」當成已確認常數。兩定位點涵蓋左緣能改善遮擋偵測，但視窗頂邊位於定位點下方時仍可能只遮色帶，必須保留每格可讀性檢查。

## 6. 上位機／橋接／Log Solution 的順序

```text
Log READY（STANDBY，或保留上輪的可交付畫面）
  → 上位機完成放料、治具與條碼準備
  → 上位機透過橋接觸發開始監控
  → Log 接受本輪、鎖定配置、禁止重複觸發、建立舊檔基準
  → 準備完成後才發布 BUSY／MONITORING
  → 橋接確認本次 MONITORING
  → 上位機觸發 ATE 開始測試
  → 各通道觀察到可信活動，HMI／色帶顯示 TESTING
  → 結果逐格更新
  → 全部配置位置終局、無待確認
  → READY／COMPLETE 或 READY／MANUAL_STOP_COMPLETE
  → 橋接確認本輪、容量、完整結果與穩定影格
  → 回報上位機，由上位機決定後續動作
```

「物料是否準備好」由上位機判斷；「可否收集新的本輪資料」由 Log Solution 負責。MONITORING 不可早於舊檔基準完成，否則 ATE 新檔可能被納入舊檔基準。

收到開始命令到 MONITORING 之間的畫面如何呈現、如何讓未準備完成的狀態不被誤認為仍可重複觸發，仍需定稿；已接受命令必須立即鎖定，不能因上一張 READY 影格再接受一輪。

## 7. TESTING 與逾時

### 7.1 TESTING 是過程觀察，不是交付前置

- 某格 TESTING 只表示該格已觀察到測試活動，不代表所有位置都開測。
- 允許 MONITORING → COMPLETE 而未觀察到 TESTING；快速測試或只有有效最終結果的來源不得因此卡住。
- 沒看到 TESTING 不等於 ATE 當機；可能是未觸發、來源未寫入、路徑／讀取問題或快速完成。

### 7.2 整輪一直沒有開始的警報：已同意

本次 FCT profile 的 start 期限先採 120 秒，之後依現場實測調整；DFU／BT 不因此一律改為 120 秒。依前次已確認，從接受開始監控起算，包含來源準備時間。

到期時，若整輪完全沒有可信測試活動，也沒有有效結果：

1. 停止本輪收集。
2. 所有未開始位置定案為 NOTEST。
3. 顯示「未偵測到測試開始」警報；REVIEW／BUSY，禁止交付。
4. 人員確認警報且沒有其他待確認後，READY／COMPLETE，保留 NOTEST 結果。
5. 不把原因擅自命名為「ATE 已當機」，不以自動重測或自動點 ATE 代替人工確認。

這是「整輪無可信開始證據」的新確認政策；部分位置已活動／已有結果而其他位置未開始時，不自動套用整輪無開始警報，沿用各位置既有期限規則。期限判定與同批新檔恰好相遇時的先後仍需在實作規格明確化；目前程式先判 deadline 再讀來源。

已 TESTING 卻超過測試期限仍未取得結果，維持既有 TIMEOUT 與整輪上限政策，不把新開始警報當成這些規則的替代。

## 8. 人工停止

- 已取得的 PASS／FAIL／NOTEST／TIMEOUT 等終局結果保留；只有未完成位置改為 STOPPED。
- 通道文字與色帶皆使用 STOPPED，色帶沿用灰色 RGB #bfbfbf。不轉成紅色 FAIL，也不另造 STOP／FAILED 別名。
- 來源尚未建立時，立即停止本輪並按配置建立完整 STOPPED 格位；不得用空集合當成結果完整。
- 延遲返回的來源準備不得覆蓋已定案結果或重啟本輪。
- 無待確認事項時顯示 MANUAL_STOP_COMPLETE；有待確認先 REVIEW。
- 即使每格都是終局、沒有任何 STOPPED 格，整輪人工停止原因仍須保留；不能靠搜尋某格 STOPPED 推測整輪原因。
- 操作員決定重工範圍；本文件不要求抹除已測結果，也不要求 Log Solution 將整輪改成 FAIL。
- 保存與重建須保留 manual_stop 事實及交付資格，不能假造一般 finished 來掩蓋人工停止。

## 9. 橋接交付規則與尚待對齊的協定

### 9.1 必須保留的驗證

1. 設備、配置容量與橋接測試通道數相符；採樣全部配置位置。
2. 定位、排數、狀態與結果色格皆可靠，影格新鮮且來源時間戳／串流檢查通過。
3. 正常自動輪次先觀察本次 MONITORING，再接受其後的可交付狀態；不能取用上輪殘留 READY 結果。
4. COMPLETE 與 MANUAL_STOP_COMPLETE 都要求全部格位為終局：PASS、FAIL、NOTEST、TIMEOUT、STOPPED。
5. 穩定確認要包含「整輪完成種類＋容量＋各格結果」，不能只比各格顏色，以免混合一般完成與人工停止的影格。
6. REVIEW、unknown、遮擋、凍結、容量不符或非終局格位不得交付；故障不可偽裝成產品 FAIL。
7. READY 上的結果持續保留到新輪開始；重傳、重啟恢復與同輪性仍依橋接既有政策處理。

### 9.2 尚未定稿，不可自行猜測

- **準備中就人工停止／來源準備期間就逾時**：可能從未對橋接顯示 MONITORING；現行 gate 因 monitoring_not_observed 不交付。需明確定義如何可靠連結這次開始請求與中止／警報後的結果，不能為了交付直接取消同輪保護。
- **人工停止回覆格式**：必須回報明確原因，建議獨立的完成種類資訊；實際 TCP 欄位／版本由橋接與 LabVIEW 規格定稿。本文件不宣稱現有 JSON 已有這個欄位。
- **TESTING 回報方式**：保留通道位置；是否新增命令／事件或擴充既有回覆，須與橋接／LabVIEW 協定對齊，不能在長輪詢連線任意插入未定義訊息。
- **第五種圖樣、幾何與準備期間的畫面表示**：完成確認及跨專案 fixtures 後，才能凍結可部署契約。

## 10. 視窗前景：已確認

開始監控、觀察到 TESTING、結果更新、整輪完成時提升視窗；同批更新合併處理，不因固定輪詢反覆提升。不永久 topmost、不呼叫 focus_force。

橋接需要看畫面時，自行透過既有自動化點選 Dock 的 Log Solution 圖示恢復可見性。原生 ATE 鍵盤焦點是否保留，須實機驗證，不能只靠假 root 呼叫驗證。

## 11. 配對部署與驗收清單

先完成支援舊 1.1 與新 1.2 幾何／圖樣的橋接，再部署 Log Solution 1.2。新圖樣與新定位點對舊 consumer 都不相容。

- [ ] 五種圖樣與未知／低對比／缺格逐一回放，驗證不誤分類。
- [ ] 一排／兩排、容量 1／10／11／20，容量外黑格不算產品結果。
- [ ] 來源準備未完成不得回報監控就緒；重複開始不建立新輪。
- [ ] TESTING 逐通道回報；沒有 TESTING 但已有可信完整結果仍可交付。
- [ ] 全輪 120 秒無可信活動／結果：NOTEST、REVIEW、確認後才交付。
- [ ] 人工停止含混合結果、全 STOPPED、全部已有終局但仍人工停止、待確認後解除。
- [ ] 準備中停止／逾時、未見 MONITORING 的同輪交付策略完成確認並測試。
- [ ] HMI、公開輪次結果、Session／audit 重建與橋接輸出一致。
- [ ] 切換完成種類時穩定計數重置，不能混用兩種完成影格。
- [ ] 左側／只遮色帶／第二排遮擋、低對比、舊圖及影格凍結拒判。
- [ ] 真 Tk 1.0／1.5 scaling 圖像交獨立 consumer replay；實際 JetKVM 與 ATE 焦點另驗。
