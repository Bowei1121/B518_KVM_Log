## 1. 給辨識開發者的重點

- 不用 OCR 判斷 READY／BUSY，以四格黑白狀態標記為依據。
- READY 是「可以接受新一輪」；不是「一定有結果」，也不是「本輪 PASS」。
- BUSY 分成 PREPARING（尚不能開測）、MONITORING（可開測）及 REVIEW（待確認）；橋接不能只看 HMI 的 BUSY 文字。
- MONITORING 的正常監控圖樣必須表示「已完成本輪來源準備，可以讓 ATE 開測」，不能只表示收到命令。
- 「待確認」對外屬 BUSY，但禁止開測／取用結果；其畫面有獨立圖樣。
- 「正常可交付」與「人工停止可交付」都是 READY，必須有不同機器圖樣；後者須明確回報上位機。
- TESTING 是通道狀態，不是另一種整輪黑白圖樣，也不是交付結果的必經條件。
- 藍框排數標記、紅框狀態標記、左右定位點各有用途，不能互相替代。

## 2. 使用者截圖中的三種標記

| 標記 | 用途 | 判讀內容 |
| --- | --- | --- |
| 藍框：水平兩格 | 排數標記 | 黑白＝一排；白黑＝兩排。不是 READY／BUSY。 |
| 紅框：2×2 四格 | 整輪狀態標記 | 待命、準備中、監控就緒、待確認、正常可交付、人工停止可交付。 |
| 左右黑底內嵌白小格 | 定位點 | 找出位置、方向、比例；不是程式工作狀態。 |

藍／紅框是使用者截圖註記，不是要加入 App 的彩色辨識框。橋接不得依賴這些彩色外框。

排數標記避免把「第二排遭遮擋」誤認成「本來只有一排」。定位點仍須先通過方向與畫質檢查，才能採樣狀態格及結果色帶。

## 3. 六種整輪狀態：已確認語意

下列名稱是文件中的辨識名稱；既有程式 enum、TCP 欄位與 HMI 文案須在實作時對齊，不表示它們現在已存在。

| 辨識名稱 | 儀器狀態／HMI | 意義 | 橋接動作 |
| --- | --- | --- | --- |
| STANDBY | READY／待命 | 可接受新一輪，沒有可交付的本輪結果 | 可以發開始監控命令，不取用色帶殘留結果 |
| PREPARING | BUSY／準備中 | 本輪開始已受理並鎖定，舊檔基準等來源準備尚未完成 | 等待 MONITORING，不啟動 ATE、不重複開始 |
| MONITORING | BUSY／監控中 | 本輪來源已準備完成，可可靠收集之後的 Log | 確認是本次開始後，通知上位機可觸發 ATE |
| REVIEW | BUSY／待確認（含異常） | 衝突、警報或啟動失敗尚待人員處理；讀檔可能繼續、已停止或尚未建立本輪 | 橋接通知上位機報警並暫停後續動作，不開測、不交付結果 |
| COMPLETE | READY／完成 | 本輪完整結果可交付，且無待確認；不是人工停止 | 穩定性與同輪性驗證後交付全部結果 |
| MANUAL_STOP_COMPLETE | READY／人工停止 | 人工停止；結果已完整定案，且無待確認 | 交付全部結果，明確回報「人工停止」，不可只報一般完成 |

規則：

1. 有待確認衝突、未確認警報或尚未復位的啟動失敗時，REVIEW 優先，不能因其他欄位為可交付就顯示 COMPLETE。
2. COMPLETE 不是全 PASS；FAIL／NOTEST／TIMEOUT 也可能是合法完整結果。
3. 人工停止後若仍有待確認，先 REVIEW，處理完才 MANUAL_STOP_COMPLETE。
4. 正常開始／完成及人工停止，通道、色帶、整輪快照、硬碟稽核重建必須一致。
5. 背景保存不單獨阻擋結果交付或下一輪 READY；保存異常仍須可見、可恢復，正常關閉仍依既有完整保存政策。
6. 啟動失敗使用 REVIEW 異常待確認，操作員排除問題、確認並復位後才回 READY；詳見第 3.1 節。不得偽造 MONITORING、完整產品結果或人工停止完成。

### 3.1 異常訊號、啟動失敗與人工復位：已確認

REVIEW 就是橋接可辨識的「異常／需人員處理」共同狀態格，圖樣為左列黑、右列白（1010）。橋接可靠辨識後，通知上位機報警並暫停後續動作；即使色帶保留上輪結果，也不得以此開測或交付。

- REVIEW 不是產品 FAIL，也不一定代表 ATE 硬體故障；它可能表示結果衝突、逾時或 Log Solution 啟動失敗。詳細原因顯示於 HMI 並保留診斷紀錄，單靠四格不能區分所有原因。
- 配置／路徑驗證等在接受本輪前失敗：記錄開始請求失敗及 App 層異常，不補造新輪、不把錯誤掛在上一輪。狀態格仍需投影 REVIEW，不能只沿用上一輪 READY／COMPLETE。
- 本輪已接受、來源建立／準備過程失敗：停止本輪，保留輪次及錯誤；REVIEW，禁止開始 ATE、禁止結果交付，不把啟動失敗改成通道 FAIL 或人工停止完成。
- 人員排除問題後，人工確認並復位；已建立本輪者取消該輪，未建立者結束這次失敗請求，保留原紀錄。之後才回 READY，下一次明確觸發才建立新輪，不自動重試或自動啟動 ATE。
- 復位是解除 Log Solution 的已處理故障與開始鎖定，不代表刪除紀錄、強制採用不確定結果，或自動重啟 ATE／操作治具。
- 「復位」是已確認政策；實際按鈕、錯誤分類與對外回報欄位須由實作規格對齊。單純關閉錯誤視窗不能視為已復位。
- 這是 Log Solution 仍可更新畫面時的異常訊號；若整個程式／畫面停滯，不能期待它更新 REVIEW，橋接仍須保留逾時及影格新鮮度／凍結檢查。

## 4. 四格圖樣配置

讀取順序固定為：左上、右上、左下、右下。B＝黑，W＝白；數值 1＝黑，0＝白。

| 狀態 | 上排 | 下排 | 位元順序 | 確認狀態 |
| --- | --- | --- | --- | --- |
| STANDBY | B W | W B | 1001 | 沿用 1.1 |
| PREPARING | W B | W B | 0101 | 準備中語意已確認；本次文件的第六圖樣技術配置 |
| MONITORING | B B | W W | 1100 | 沿用 1.1 圖樣，收緊成來源已準備完成 |
| REVIEW | B W | B W | 1010 | 沿用 1.1 圖樣；擴充為啟動失敗等異常的共同待確認訊號 |
| COMPLETE | W B | B W | 0110 | 沿用 1.1，保留一般可交付語意 |
| MANUAL_STOP_COMPLETE | W W | B B | 0011 | **2026-10-19 使用者已確認** |

第五種圖樣示意（2026-10-19 已確認）：

```text
┌─────┬─────┐
│ 白  │ 白  │
├─────┼─────┤
│ 黑  │ 黑  │
└─────┴─────┘
```

新增 PREPARING 的 0101 示意為上排白黑、下排白黑；它不能讓橋接啟動 ATE。

此配置保留既有四個圖樣，六種使用全部恰好兩黑兩白的組合；任何單一格的黑白翻轉不會變成另一個合法圖樣。但它不是錯誤校正保證，不能省略畫質、穩定影格及遮擋檢查。

未定義圖樣（例如全黑、全白，或只有一黑／三黑）、缺格或低對比都回 unknown，不猜成最接近狀態。0101 已配置為 PREPARING，不再是未知圖樣。舊 1.1 consumer 不認得兩種新增圖樣，必須先更新橋接才能部署 App。

## 5. 排數、幾何與取樣

### 5.1 已沿用的內容

- 每排固定 10 格；容量 1–10 顯示一排，11–20 顯示兩排。超出配置容量的位置為黑色，不是產品 FAIL。
- 排數：BW＝一排、WB＝兩排；BB／WW／缺失／低對比均拒判。
- 狀態格 2×2，每格 10×10 Tk 單位，間隔 2，白色 quiet zone 2，總尺寸 26×26。
- 灰階 0–80 判黑、176–255 判白，81–175 不可靠；這是最低取樣規則，不是實際 JetKVM 壓縮容差已驗收。
- Tk 單位不是實體像素；橋接必須由定位點量測比例。

### 5.2 幾何變更：方向已同意、精確座標待驗

移除 `KVM RESULT` 字樣，左定位點移至第一格色帶正上方；其他定位點、排數格、狀態格及結果色帶位置維持。

| 右定位點 | (320, 2)，22×22 | 維持 |

四周須至少 2 單位白留白，維持左右不對稱內嵌白格；不與其他標記／色帶重疊。第一格 x=0 與左側留白須以父框範圍、實際畫面及裁切驗證，不可直接假設負座標有效。

## 6. 上位機／橋接／Log Solution 的順序

```text
Log READY（STANDBY，或保留上輪的可交付畫面）
  → 上位機完成放料、治具與條碼準備
  → 上位機透過橋接觸發開始監控
  → Log 接受本輪、鎖定配置、禁止重複觸發
  → BUSY／PREPARING，建立舊檔基準；橋接只能等待
  → 準備完成後才發布 BUSY／MONITORING
  → 橋接確認本次 MONITORING
  → 上位機觸發 ATE 開始測試
  → 各通道觀察到可信活動，HMI／色帶顯示 TESTING
  → 結果逐格更新
  → 全部配置位置終局、無待確認
  → READY／COMPLETE 或 READY／MANUAL_STOP_COMPLETE
  → 橋接確認本輪、容量、完整結果與穩定影格
  → 回報上位機，由上位機決定後續動作
```

「物料是否準備好」由上位機判斷；「可否收集新的本輪資料」由 Log Solution 負責。MONITORING 不可早於舊檔基準完成，否則 ATE 新檔可能被納入舊檔基準。

收到開始命令到 MONITORING 之間顯示 BUSY／準備中及 PREPARING 圖樣；已接受命令必須立即鎖定，不能因上一張 READY 影格再接受一輪。PREPARING 可能很短、橋接可能未採到；開測仍必須實際確認 MONITORING，不要求一定看過 PREPARING。

## 7. TESTING 與逾時

### 7.1 TESTING 是過程觀察，不是交付前置

- 某格 TESTING 只表示該格已觀察到測試活動，不代表所有位置都開測。
- 允許 MONITORING → COMPLETE 而未觀察到 TESTING；快速測試或只有有效最終結果的來源不得因此卡住。
- 沒看到 TESTING 不等於 ATE 當機；可能是未觸發、來源未寫入、路徑／讀取問題或快速完成。

### 7.2 整輪一直沒有開始的警報：已同意

本次 FCT profile 的 start 期限先採 120 秒，之後依現場實測調整；DFU／BT 不因此一律改為 120 秒。依前次已確認，從接受開始監控起算，包含來源準備時間。

到期時，若整輪完全沒有可信測試活動，也沒有有效結果：

1. 停止本輪收集。
2. 所有未開始位置定案為 NOTEST。
3. 顯示「未偵測到測試開始」警報；REVIEW／BUSY，禁止交付。
4. 人員確認警報且沒有其他待確認後，READY／COMPLETE，保留 NOTEST 結果。
5. 不把原因擅自命名為「ATE 已當機」，不以自動重測或自動點 ATE 代替人工確認。

這是「整輪無可信開始證據」的新確認政策；部分位置已活動／已有結果而其他位置未開始時，不自動套用整輪無開始警報，沿用各位置既有期限規則。期限判定與同批新檔恰好相遇時，已確認維持先判 deadline 再讀來源：本次輪詢已到期限、但程式尚未接受可信證據時，先依期限定案；不以該次後讀到的 TESTING／結果或檔案自報的較早時間挽回已到期狀態。期限前已接受的結果／活動仍保留。

已 TESTING 卻超過測試期限仍未取得結果，維持既有 TIMEOUT 與整輪上限政策，不把新開始警報當成這些規則的替代。

## 8. 人工停止

- 已取得的 PASS／FAIL／NOTEST／TIMEOUT 等終局結果保留；只有未完成位置改為 STOPPED。
- 通道文字與色帶皆使用 STOPPED，色帶沿用灰色 RGB #bfbfbf。不轉成紅色 FAIL，也不另造 STOP／FAILED 別名。
- 來源尚未建立時，立即停止本輪並按配置建立完整 STOPPED 格位；不得用空集合當成結果完整。
- 延遲返回的來源準備不得覆蓋已定案結果或重啟本輪。
- 無待確認事項時顯示 MANUAL_STOP_COMPLETE；有待確認先 REVIEW。
- 即使每格都是終局、沒有任何 STOPPED 格，整輪人工停止原因仍須保留；不能靠搜尋某格 STOPPED 推測整輪原因。
- 操作員決定重工範圍；本文件不要求抹除已測結果，也不要求 Log Solution 將整輪改成 FAIL。
- 保存與重建須保留 manual_stop 事實及交付資格，不能假造一般 finished 來掩蓋人工停止。

## 9. 橋接交付規則與尚待對齊的協定

### 9.1 必須保留的驗證

1. 設備、配置容量與橋接測試通道數相符；採樣全部配置位置。
2. 定位、排數、狀態與結果色格皆可靠，影格新鮮且來源時間戳／串流檢查通過。
3. 正常自動輪次先觀察本次 MONITORING，再接受其後的可交付狀態；不能取用上輪殘留 READY 結果。
4. COMPLETE 與 MANUAL_STOP_COMPLETE 都要求全部格位為終局：PASS、FAIL、NOTEST、TIMEOUT、STOPPED。
5. 穩定確認要包含「整輪完成種類＋容量＋各格結果」，不能只比各格顏色，以免混合一般完成與人工停止的影格。
6. REVIEW、unknown、遮擋、凍結、容量不符或非終局格位不得交付；故障不可偽裝成產品 FAIL。
7. READY 上的結果持續保留到新輪開始；重傳、重啟恢復與同輪性仍依橋接既有政策處理。

### 9.2 未觀察到本次監控就緒就人工停止：已確認

2026-10-19 使用者同意下列處理：

1. Log Solution 立即停止本輪；依配置建立完整格位，既有終局結果保留、未完成格為 STOPPED。若無待確認事項，顯示 MANUAL_STOP_COMPLETE；有待確認則先 REVIEW。
2. 橋接若尚未可靠觀察到本次監控就緒（MONITORING），即使看到人工停止圖樣及完整結果，也不自動交付該結果。
3. 橋接向上位機回報「需人工核對」，暫停自動後續動作；不可把畫面視為本次已確認結果，不得推測為全部 FAIL 或自動重新測試。
4. 理由是尚無本次 MONITORING 的同輪證據，無法可靠排除上一輪殘留畫面；保留 monitoring_not_observed 的保護目的，不能為了交付取消此條件。
5. 上位機收到的是「需人工核對」處置，不是「已確認本輪人工停止結果」；人工核對後採第 9.4 節的取消本輪流程，實際協定欄位另行定稿。

### 9.3 來源準備逾時且未觀察到本次監控就緒：已確認

2026-10-19 使用者進一步同意，來源準備卡住並逾時、橋接尚未看見本次監控就緒（MONITORING） 時，採用相同的同輪保護：

1. Log Solution 顯示逾時警報，未確認時維持 REVIEW，不放行結果；格位與逾時處置依既有期限政策，不因本節把所有逾時改為人工停止。
2. 即使人員已確認警報，橋接仍因缺少本次 MONITORING 的同輪證據，向上位機回報「需人工核對」，不自動交付結果、不自動重測。
3. 警報已確認不等於橋接已證明畫面屬於本輪；不得以確認警報代替同輪性驗證。
4. 與人工停止相同，人工核對後採第 9.4 節的取消本輪流程；對外協定欄位尚待定稿。

### 9.4 人工核對後取消本輪：已確認

此節適用於第 9.2／9.3 節因缺少本次 MONITORING 證據而需人工核對的路徑：

1. 暫停後續自動動作，操作員核對狀況並取消本輪；不提供強制把不確定畫面當成本輪結果交付的操作。
2. 保留原輪次、已取得結果、警報／停止／核對與取消紀錄，不刪除、不覆寫、不把取消記成產品 FAIL。
3. 操作員決定重工範圍，排除問題並完成測試前準備後，才明確開始新輪；系統不得自動重測。
4. 橋接／LabVIEW 使用新的輪次 ID；Log Solution 亦建立新的本地輪次。兩邊 ID 角色不同，不宣稱單靠 ID 就證明畫面同輪。
5. 新輪仍須重新觀察 MONITORING 後才啟動 ATE；舊畫面與舊回覆不得替新輪完成交付。
6. 此取消決策不改變其他已可靠保存、已確認同輪結果的正常重傳政策。

看到 PREPARING 只證明正在準備，不能取代 MONITORING 的開測確認，也不能用來放寬第 9.2／9.3 節的交付保護。

### 9.5 尚未定稿，不可自行猜測

- **人工停止回覆格式**：必須回報明確原因，建議獨立的完成種類資訊；實際 TCP 欄位／版本由橋接與 LabVIEW 規格定稿。本文件不宣稱現有 JSON 已有這個欄位。
- **TESTING 回報方式**：保留通道位置；是否新增命令／事件或擴充既有回覆，須與橋接／LabVIEW 協定對齊，不能在長輪詢連線任意插入未定義訊息。
- **精確幾何及實際圖像驗收**：左定位點座標仍待驗證；準備期間畫面已定為 PREPARING／BUSY，六種圖樣仍須完成跨專案 fixtures 與驗收，才能凍結可部署契約。
