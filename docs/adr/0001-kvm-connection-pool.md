# 1. 引入 KVM 連線池與自動保活淘汰機制

Date: 2026-10-06

## Status
Accepted

## Context
原有的 `ui_app.py` 中只有單一的 `JetKVMClient` 實例，當 LabVIEW 要求不同 IP 的測試機畫面時，中繼站會中斷現有連線並啟動新的 WebRTC 連線（包含 Signaling 與 ICE 打洞）。這導致切換設備時產生高達數秒的延遲，嚴重影響多設備並行測試的產線效能，且頻繁的連線中斷容易觸發連線狀態不同步的系統錯誤。

## Decision
我們決定引入 `KVMConnectionPool` 來常駐管理多台 KVM 連線：
1. **閒置淘汰 (Idle Timeout)**：連線閒置超過 10 分鐘（未收到 LabVIEW 指令）時，主動斷開連線以節省上位機與 KVM 資源。當新指令進來時自動重新連線。
2. **自動保活 (Heartbeat)**：對於正在使用中的連線，在閒置幾秒後自動於背景觸發抓取影格，確保 WebRTC 通道暢通並偵測 KVM 異常斷線。

## Consequences
- **Pros**: 顯著消除切換測試機時的 WebRTC 重連延遲，提升並行吞吐量。增強連線的強健性與可預測性。
- **Cons**: 需增加背景執行緒或非同步迴圈對連線生命週期的管理複雜度。

## 補註（2026-10-16）
使用中連線（有指令正在執行 `acquire_connection` 租約）的心跳失敗時的規定，補充於原決定：
1. 心跳失敗的使用中連線不派給新請求；新請求取得連線時回報連線失敗（沿用既有錯誤碼 `kvm_connect_failed`），不等待也不替換正在被使用的連線。
2. 指令結束歸還時：若心跳已恢復，保留連線；若心跳仍未恢復，才淘汰。
3. 未使用中的連線，心跳失敗或斷線仍立即淘汰，原規定不變。
4. 連線已斷線（`connected` 為 False）時，新請求仍照舊重新建立連線。

## 補註（2026-10-19，#58）
死亡判定與心跳改為以下規定，取代上面「心跳失敗」相關的描述：
1. 連線是否健康只看兩種訊號：影像軌道 `recv()` 結束，或 peer connection 變成 `failed`／`closed`（`JetKVMClient.is_healthy()`）。影格太舊不算死亡，仍由 Freeze Guard 回 `frame_frozen`；`disconnected` 為暫態，也不算死亡。
2. 心跳改為詢問 `is_healthy()`，不再拉取影格。原本的影格拉取只讀快取，不會產生網路流量，對保活沒有作用。
3. 死亡訊號不會恢復，所以「心跳失敗後又恢復」的情況不再發生，上面第 2 條「心跳已恢復則保留連線」不再適用：使用中的連線不健康時，不派給新請求，租約歸還時淘汰。
4. 指令執行中連線死亡，`check_start`／`check_finish`／`inspect` 的長輪詢立即回 `kvm_connect_failed`，不等 Freeze Guard 門檻，不新增錯誤碼。
