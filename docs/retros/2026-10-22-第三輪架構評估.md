## 1. 一句話總結

## 5. 關鍵決策

| 決策 | 理由 | 決定者 |
| --- | --- | --- |
| 加入 Log Solution 心跳（每 0.5 秒 16 態） | PTS 只能證明串流活著，偵測不到 Mac／App 當機 | 使用者提出 |
| 連續 3 張有效同圖才判心跳停止 | 與 Log Solution 對齊；16 態可避開取樣的混疊（aliasing） | 使用者＋Log Solution |
| 橋接只支援顯示契約 1.3 | 簡化判讀；代價是橋接必須與 App 同時部署 | 使用者 |
| 1 倍輸出（每小格 10 px）也要可讀 | 模擬顯示 1.5 Mbps 下可讀率約 98% 且沒有讀錯 | 使用者 |
| 既有讀錯併入 #95 一起修 | 讀錯比讀不到嚴重，不能等 | 使用者 |
| 接受兩段色遮擋的殘留風險 | 現場極難發生；完全擋掉需要另一套判讀 | 使用者 |
| `core_status` 診斷不進 LabVIEW 的 `status` | 避免動到協定 1.0 | 主 session 建議 |

## 6. 做得好的地方 👍

- **審查用 mutation 驗證測試**：故意改壞程式，看測試會不會失敗。多次抓到「測試其實測不到」，例如色表拿自己比自己、遮擋寬度漏測、記錄點沒測。
- **把「讀錯」和「讀不到」分開評估**：讀取器任何放寬都先用 codec_stress 和對抗案例證明 misread 為 0。
- **使用者一句「我擔心解析度」直接變成量化模擬**：模擬找到真實缺陷（#95），以及 main 上原本就有的讀錯。
- **分波平行**：先看清票與票之間的檔案重疊再排順序，衝突只出現一次（#86／#87），以 rebase 後再審解決。
- **issue 勾選回補**：換一台電腦看 issue，也知道哪些做完、哪些沒做。

## 9. 下次可以沿用的做法

1. 大型重構先做架構評估，再用 grilling 把決策問清楚，才開票。
2. 開票時就標出檔案重疊與 blocked-by，據此排平行波次。
3. 實作、審查分 session；審查一律附 mutation 證據；修正後必須再審。
4. 審查完在 issue 勾選並留結論；主 session 合併前核對勾選。
5. 有風險的判讀改動，必須有「讀錯 = 0」的量化證據。
6. 大任務結束時寫復盤（本文件格式）。
