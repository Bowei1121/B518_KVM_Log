## 1. 一句話總結

現場發現 LabVIEW 跑 `check_finish` 長輪詢時，pop-out 滑鼠鍵盤整段失效；改成只在 Core 真的送 HID 時才擋手動操作，並把「手動 → 自動」的鍵鼠交接做到不卡鍵、不誤按、不誤報。經過 8 輪審查後合併。

## 2. 目標與成果

| 目標 | 成果 | 達成 |
| --- | --- | --- |
| check 等畫面時可手動操作 | `DeviceLockManager` 記錄持有者；`check_start`／`check_finish` 未點 Dock 時放行 `hid` | ✅ |
| Core 送 HID 時仍擋 | `start_test`／`input`／`monitor_start` 與 check 點 Dock（`dock_recovering`）回 `device_busy` | ✅ |
| UI 提示被忽略 | pop-out 狀態列節流顯示「設備正在執行自動指令，手動操作已忽略」 | ✅ |
| 交接不卡鍵（審查追加） | remote／intent 模型；第一筆自動 HID 前確認釋放；結束時只釋放不重播按下；UI busy 後合成 `release_only` | ✅ |
| 錯誤歸屬正確（審查追加） | 手動 RPC 使用獨立 JSON-RPC id 空間 | ✅ |
| 實機驗證 | 尚未進行 | ❌ |

## 5. 關鍵決策

| 決策 | 理由 | 決定者 |
| --- | --- | --- |
| 只在 Core 真的送 HID 時擋 | 現場 check 長輪詢期間需要操作 | 使用者 |
| `start_test`／`input`／`monitor_start` 一取得鎖就擋（保守） | 預檢與動作邊界不易逐一界定 | Claude，審查接受 |
| 交接只釋放、絕不重播被拒的按下 | 被拒操作必須零 HID（ADR-0005／PROTOCOL §5.6） | 審查推動 |
| 手動 RPC 獨立 id 空間 | 晚到錯誤任何時間都不能被 flow 認領 | 審查推動 |
| 釋放要等裝置 ACK（1 秒） | 非同步 USB 錯誤時不可帶修飾鍵點擊 | 審查推動 |

## 6. 做得好的地方 👍

- 每輪修正都補了「把修正改回去會失敗」的回歸測試，後幾輪特別用實際 `HidSender`＋JSON 入口驗證。
- 第 4 輪起改成明確的狀態模型（remote／intent、只釋放），之後收斂得比逐案補洞快。
- 審查以假 KVM／DataChannel 定序重現，每項都有可執行的反例。

## 7. 問題與根因 🔧

| 問題 | 根因 | 處置 | 預防 |

## 9. 下次可以沿用的做法

1. 兩個 HID 來源共用一台設備時，先定義「目標機持有狀態」與「操作員意圖」，交接規則只允許釋放。
2. 每個審查反例都寫成定序測試，並確認改回舊碼時會失敗。
3. 終止條件用嚴格遞減的不變量，不用固定輪數或過期表。
