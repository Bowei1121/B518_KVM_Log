## 1. 一句話總結

為了週一客戶看線，修好 1920×1080 下 BT Start All 找不到、monitor_start 讀不到 Log Solution 的問題，DFU 改用固定螢幕矩形定範圍，並讓 pop-out 可以直接操控目標電腦；根因都不是解析度本身，而是搜尋範圍與 scale 1.0 下的 H.264 色偏。

## 5. 關鍵決策

| 決策 | 理由 | 決定者 |
| --- | --- | --- |
| 不改解析度設定，改搜尋範圍與讀取器 | 根因是範圍與色偏，不是解析度 | Claude 分析、使用者同意 |
| 深層環放寬只限 `scale < 1.4`、距離 ≤ 42、非 OUTSIDE | 避免把 NOTEST 紫或真 STOPPED 誤吃進來 | Claude |
| DFU 用固定螢幕矩形而非視窗模板 | DFU 視窗底色隨 ATE 模式變，模板不可信 | 審查後調整 |
| 缺 `DFU_region.json` 時自動建全螢幕預設 | 現場先能跑，再收斂範圍 | 使用者 |
| 實作 Sonnet、審查 Codex，通過才合併 | 分工與品質把關 | 使用者 |

## 6. 做得好的地方 👍

- 從相似度 0.52 和視窗 box 推出「按鈕在模板寬度外」，沒被「解析度」假設帶走。
- 用模擬編碼量化碼率門檻；審查端再用繁忙桌面補數據，戳破「1.5 Mbps 以上全可靠」的說法。
- 錯誤訊息加 last reading reason，現場失敗時能直接分辨沒畫面、標記讀不到或心跳問題。
- DFU 同類問題預防性一起修，沒等現場爆。

## 7. 問題與根因 🔧

| 問題 | 根因 | 處置 | 預防 |
| --- | --- | --- | --- |
| Start All 相似度 0.52 | ROI 用 `found.width`，按鈕在視窗模板右側之外 | ROI 延伸到畫面邊緣＋全畫面 fallback | 搜尋範圍不要綁模板尺寸 |
| monitor_start 3 秒找不到 | 測試治具是 Retina 2×，現場 1×；H.264 色偏讓 WAITING 偏向 STOPPED | 低 scale 深層環放寬；要求高碼率 | 測試涵蓋 scale 1.0＋真編解碼（#190） |
| #189 第一版 CI 16 失敗 | `Box` 不可索引；測試模板重複存檔 | `tuple(box)[:2]`、`overwrite=True` | 子 session 先跑相關測試再推 |
| macOS 全量 pytest 卡數小時 | Tk 測試在 macOS 卡住 | 只跑相關測試檔 | 以 CI 為準，本機跑 targeted |
| #188 PR 內文碼率說法過度推廣 | 只用簡單 WAITING 畫面模擬 | 審查數據記進 #190 | 模擬要用接近現場的繁忙畫面 |

## 9. 下次可以沿用的做法

1. 「找不到」類問題先看分數與搜尋框，再懷疑解析度。
2. 測試治具與現場 scale 不同時，一定補現場 scale 的測試。
3. 視覺判讀的改動要配真實編解碼數據，且用接近現場的畫面。
4. 錯誤訊息帶上最後一次失敗原因，現場除錯成本最低。
5. 主 session 分析、Sonnet 實作、Codex 審查，審查建議即時開成 issue。
