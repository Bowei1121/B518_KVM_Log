## 1. 一句話總結

現場除錯時找不到失敗當下的圖（`latest/` 每次動作都會被清掉），所以在 `match_diagnostics` 加上 24 小時的 JPEG 歷史歸檔，並補存 `monitor_start` 確認期的失敗影格。經過 5 輪審查，修掉 9 個並行／容錯問題後才合併。

## 2. 目標與成果

| 目標 | 成果 | 達成 |
| --- | --- | --- |
| `latest/` 行為不變 | 仍是 PNG + `summary.json`，`load()` 相容 | ✅ |
| 每次動作歸檔到 history | `history/<YYYYMMDD>/<HHMMSS_mmm>_<operation>_<OK\|FAIL>[_N]/`，只存 JPEG（品質 85） | ✅ |
| 保留 24 小時、上限 2048 MB | 每次歸檔後清掃全部裝置；超時刪除、超量從最舊刪起、空日期資料夾一併刪 | ✅ |
| IO 例外不影響流程 | 歸檔、排程、清理、確認期 record 全部 best-effort 並記 log | ✅ |
| 補存確認期失敗影格 | `confirm_last_unreliable`，含最後一張不可靠影格與雙語 last_reason | ✅ |

| 現場驗證 | JetKVM 實機、Windows 磁碟未實測 | ⚠️ |

## 5. 關鍵決策

| 決策 | 理由 | 決定者 |
| --- | --- | --- |
| 保留 24 小時、history 只存 JPEG、`latest/` 不變 | 現場要回頭找失敗圖；JPEG 省空間；UI 相容 | 使用者 |
| 設定用模組常數加建構子參數 | repo 沒有適合的共用設定機制，6 個呼叫點都直接建構 | Claude（寫進 PR 說明） |
| 背景單一 daemon worker | 不卡 Core event loop；同程序內序列化寫入與清理；Core 退出不等 | Claude（回應第 1、2 輪） |
| 佇列滿了就略過該次歸檔 | 磁碟卡住時不累積記憶體；`latest/` 仍完整，可接受遺失歷史 | Claude（回應第 2 輪） |
| 暫存 + 原子 rename，不加跨程序鎖 | 鎖在 Windows／macOS 的可攜性與死鎖風險較高；用 mtime 過期加整段重試就能涵蓋已知競爭 | Claude（審查接受） |
| 最後一輪的文字建議不改 | 改了會換 HEAD 又要重審；只影響文件措辭 | Claude |

## 6. 做得好的地方 👍

- 每輪審查的每一項都對應一個回歸測試，並在 PR comment 列出測試名稱，審查端可以直接重跑驗證。
- 用真實子程序測跨程序競爭（`test_other_process_mid_write_survives_our_cleanup`），不是只靠 mock。
- 合併時用 `--match-head-commit` 鎖定審過的 HEAD。
- 審查者會實際重現故障（慢掃描、子程序退出、雙發布者），每輪的問題都是真的，沒有誤報。

## 7. 問題與根因 🔧

| 問題 | 根因 | 處置 | 預防 |
| --- | --- | --- | --- |
| 審查跑了 5 輪 | 初版把「歸檔是 best-effort 的附屬功能」當成單純 IO，沒有先列出它的並行模型（event loop、執行緒、多程序共用 root、程序退出） | 每輪補一層 | 動到共用目錄或背景工作前，先在 PR 說明寫出並行與失敗模型清單（誰會同時寫、退出時怎樣、滿了怎樣、寫一半怎樣） |
| 同步 IO 卡住 TCP event loop | `finalize()` 在 async 流程的 `finally` 被同步呼叫 | 改背景 worker | 在 Core 流程裡新增 IO 時，預設移出 event loop |
| 跨程序競爭漏了兩次 | 只想到 Core 單一程序，沒注意 `jetkvm_auto` 和第二個 Core 也會寫同一個 template root | mtime 過期判斷 + 整段重試 | 設計共用目錄時先 grep 所有會寫入該 root 的進入點 |
| 本機測試環境花了不少時間 | Anaconda 的 pytest 太舊；opencv 新版沒有對應 wheel，pip 改從原始碼編譯，看起來像卡住 | 在 scratchpad 建 venv，`--only-binary=:all:` 固定 `opencv-python-headless<4.11`、`numpy<2` | 把本機測試 venv 的建立指令寫進文件，或提供固定版本的 requirements-dev |
| 背景寫入讓既有測試偶發失敗 | `TemporaryDirectory` 清理時，背景 worker 還在寫 | 測試在 `finalize` 後呼叫 `wait_for_history()` | 新增背景工作時，同時提供測試用的 flush 介面 |

1. 審查修正回覆的格式：每項寫「修法 + 回歸測試名稱 + 斷言」，審查端比對最快。
